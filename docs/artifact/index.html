Jevlet: typed, calibrated decisions next to a 4B agent on an embedded NPU

A confirm gate can only act on what it can see. This page measures how much of TypeSafe's Jev idea (typed questions, calibrated probabilities, no text generation) can be served locally beside an offline network-management assistant, and what it buys the gate.

The surface this is for

The assistant turns an operator's sentence into one switch command; a human approves every write. Today the card shows the command and the model's own reason. With a decision layer it also shows one typed check with a probability the deployment has calibrated on its own labeled rows.

Operator: “@sw1 the camera on 5 needs a power cycle — cut it for now”

Where the generative agent fails

Two properties matter more than the headline number. The misses are structured, and the model emits no probability: a generated tool call is one-hot, and the compiled NPU runtime returns "logprobs": null (measured live, GenieX v0.4.0; no version ships n_probs).

The readout also flags 7 of 13 “diagnose instead of read” calls and false-flags 2 of the 10 format slips that do match the request. The 0.8B readout is a real middle point once its thinking block is disabled: it catches 13 of the 20 confusions but lets 25 dangerous swaps through and flips 95% of its tool answers across option orderings. The fine-tuned encoders do not learn the gate from this data: round 1's head learned the class prior (it says “no” to 93% of correct proposals), and a class-balanced gate-only model (2,080 balanced pairs, 6 epochs) stays at AUROC 0.56 — it accepts 79% of wrong-port proposals, which is the tell: the gate needs the proposed port and value compared with the request, and a 150M encoder trained on synthetic swaps does not get that from ~2k pairs. The decoder readouts do.

The adversarial rows and order sensitivity

On the 259 authored rows (confusables, symptom-first, out-of-scope, other tools) the readout drops to tool 68.3% / command 60.2% (64.1% allowing listed alternatives; 84.3% / 67.4% on the 81 adversarial confusables) — and its answers flip between option orderings on 36% (tool) and 29% (command) of rows. Averaging three rotations recovers 4 and 0 points over a single ordering, and after grouped temperature scaling zero command errors sit above 0.9 confidence (51 did raw). The most common miss is mapping out-of-scope messages onto show_cable_diagnostics.

A 0.8B decoder (Qwen3.5-0.8B) reads out nothing in its default template — its first generated token opens a thinking block, so no label mass exists. With thinking disabled it scores tool 74.6% / command 35.0% / is_write 81.9% / touches_poe 80.8% on the 260 base rows, with 71–84% of the mass on the labels and a 95% order-flip rate on the tool question (averaging three rotations lifts it from 68.8% to 74.6%). Small decoders can carry the interface; they cannot yet carry the 24-way question.

Co-tenancy. A generative turn through the production NPU runtime (96-token answer) took 4.43–4.52 s idle and 4.32–4.33 s while the CPU readout was answering a continuous stream of questions: no measurable interference. The CPU decision layer and the NPU agent share nothing but memory bandwidth.

Serving-path facts

  • GenieX v0.4.0 (production, compiled W4A16): logprobs: null, max_tokens ignored (3 tokens for a 1-token request), cached_tokens: 0. A typed decision on this path is a text label: measured live, a 4-way tool label scored 88.7% vs 93.3% for the model's own tool call, a 24-way command label 70.8% vs 83.1%, with 7% of labels flipping on reversed option order.
  • Upstream llama-server, Hexagon backend: has n_probs/logprobs, the lm-head runs on the CPU on every path; built, not deployed; cannot share the NPU with the production tenant (session error 0x80000406 at startup when it tries).
  • Board CPU: the same binary runs CPU-only next to the NPU tenant once the Hexagon device count is set to zero. This is where the readout and every encoder above live in production.

The dataset

519 evaluation rows and 983 training paraphrases, sanitized (@sw1, no addresses). 65 canonical seeds in four difficulty levels; 195 paraphrases (casual, verbose, indirect); 81 adversarial confusables written to sit between adjacent commands; 54 symptom-first diagnostics; 76 documentation / out-of-scope / fleet-wide messages; 48 requests for tools outside the production 4-tool profile. Authored rows carry is_write, touches_poe_power, ambiguity 0–3 (35 rows at 2, 1 at 3), alt_ok, blast; they were generated by one LLM and verified row-by-row by another, with every change logged. Human review is pending. All splits are grouped by seed request.

What holds, what doesn't

  • Routing through the model under test buys no accuracy; a text label from the 4B is worse than its tool call. The readout's value is the probability, and only after calibration on this domain's rows.
  • Order bias is not a rounding error on the hard rows (29–36% flips). Rotation averaging is the cheapest fix and costs K requests.
  • Zero-shot open decision models are honest and fast but at chance on the gate; above ~6 options the 151M encoder collapses. Hierarchical questions or fine-tuning, not longer descriptions.
  • A 150M encoder fine-tuned on ~2,000 examples with the question order shuffled (8 epochs) is the better router on identical held-out rows — 88.1 / 77.8 / 95.2 / 96.8 vs the 4B readout's 84.9 / 69.8 / 90.5 / 96.0 — at 126 ms per question on the board CPU. No encoder variant learns the gate from this data (AUROC 0.53–0.65); the gate stays with the decoder readout (0.95 for the 4B, 0.88 for the 0.8B).
  • The division of labor on the board writes itself: encoder for the per-turn router and pre-check, readout for the per-write gate.
  • On the board, one gate check costs 3 s from the 4B readout and 0.18 s from the 150M encoder; a four-question router battery costs 5 s and 2.5 s. The encoder is the per-turn option; the readout is the per-write option.
  • Limitations: LLM-authored labels pending human review; one domain; N in the hundreds; no cloud Jev run (no key).
