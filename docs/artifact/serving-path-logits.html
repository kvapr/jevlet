Where the logits go: what each way of running the 4B exposes to a decision layer

A typed decision needs the probability distribution at the first generated position, and on this board only the paths that run on the CPU return one where a decision layer can live. This page records what each serving path exposes, what the text-label fallback costs, why the two NPU (neural processing unit) runtimes are out, and what the deployed choice costs beside the running agent.

No new measurement was taken for this page. N is in the hundreds throughout, and the authored labels are LLM-written and LLM-verified, human review pending.

What the layer needs from a serving path

The readout backend sends one request per question. The instructions, the option legend with single-token labels and the answer format go in the system message, so they are identical across states; the state goes in the user message. It asks for one token at temperature 0 with log-probabilities on, and reads the distribution at the first generated position: mass on each label's case and whitespace variants is summed and renormalised over the label set. Three things have to hold for that to work.

POST /v1/chat/completions {"messages": [{"role": "system", "content": "<instructions, option legend, answer format>"}, {"role": "user", "content": "<the state>"}], "max_tokens": 1, "temperature": 0, "logprobs": true, "top_logprobs": 40, "cache_prompt": true, "chat_template_kwargs": {"enable_thinking": false}} → choices[0].logprobs.content[0].top_logprobs the label variants, summed → timings.prompt_n tokens actually evaluated
  • Pre-sampling probabilities at position 0. Not a sampled token, not a parsed sentence: the softmax over the vocabulary before anything is chosen. Without it there is no probability, no confidence and nothing to calibrate.
  • max_tokens honoured. One decoded token is the whole cost of the answer. A runtime that generates a sentence anyway pays for a sentence.
  • A prefix cache. The legend is the constant part of every prompt. With the cache, a question costs the state's tokens only: 20 evaluated tokens of a 425-token prompt for the tool question on this board.

An encoder skips all three: one forward pass over the state and the questions returns a distribution per question directly. That is why it appears below as the fifth place to send the request.

Path 1: the compiled production runtime

Two probes went to the production server, the request above with top_logprobs 5. The answer was a sentence fragment and three empty fields.

→ GenieX v0.4.0, compiled W4A16 bundle, NPU content: "No." completion_tokens: 3 logprobs: {"content": null, "refusal": null} prompt_tokens_details.cached_tokens: 0
no probabilitythe Go front end parses the OpenAI request struct but nothing implements it: the runtime binaries on hand contain 0 strings for n_probs and 0 for llama_get_logits; the 38 hits for logprobs are SDK and OpenAPI type names.
no prefix cachethe runtime resets the dialog after every query, which clears the KV cache in place; cached_tokens is 0 on every request, so each question re-prefills the whole legend.

What remains on this path is a text label: ask for the single letter of an option and parse it. That was measured live on the 195 paraphrases through the production runtime, against the model's own tool call on the same rows (its command accuracy counts a bare-command format slip with the right command as correct, and its tool accuracy is 90.3% raw, 93.3% once those slips are normalised).

"Own call" is the model's own tool call on the same rows (tool normalised, command semantic); latency is the median through the production runtime. The 4-option tool question is the production profile. The two tool rows agree in total (173 of 195 right; the command label gets 138) and disagree on 14 of the 195 rows (7%): the same row gets a different label depending on where its option sits in the list, and there is no probability with which to notice. On the indirect slice the text label reaches 75.4% where the normalised tool call reaches 86.2%. 65 rows per style, so single-style gaps of a few points are within noise.

The label is fast, 0.43 s for four options, and it is the wrong tool for the job. Routing through the model under test costs accuracy on both questions and returns no number the confirm card could show. The design notes list "replacing the generative tool caller" as a non-goal for this reason.

Path 2: the 0.5.1-alpha evaluation binary

A newer GenieX ships a llama.cpp backend selected with -c npu. It runs a GGUF on the Hexagon NPU through the same ggml-hexagon lineage as the upstream package, and it is the path on which the 98.5% canonical-bench and 14.5 s per turn figures below were produced. For a decision layer it changes nothing. Its front end has no n_probs plumbing either (0 binary hits), so a completion returns text and nothing else; max_tokens is honoured, and whether the prefix survives between requests was not established. It is an evaluation binary, not the deployed runtime. The version label moved, the interface did not.

Path 3: upstream llama-server on the Hexagon backend

This is the only NPU path that exposes what the layer needs. In the llama.cpp server, a raw /completion takes n_probs, post_sampling_probs and logit_bias; on /v1/chat/completions, logprobs:true with top_logprobs:N maps onto n_probs (default 20). The probabilities are a full-vocabulary softmax of the pre-sampling logits, and requesting them turns backend sampling off so the logits always come to the host. On this backend they were never going to be anywhere else: ggml-hexagon.cpp refuses any matrix multiply wider than 32,768 rows, which is the lm-head, so the logits are computed on the CPU from the last hidden state on every path. cache_prompt and slot save/restore exist; whether HTP-resident KV survives a slot restore is unverified.

The package exists: bin/llama-server with libggml-hexagon.so and the HTP libraries for v73, v75, v79 and v81, built from llama.cpp commit cb295bf. It has never been run on this board, because the NPU is a single tenant. Starting the binary while the production runtime holds the device fails at the first DSP session and the process aborts.

0x80000406ggml-hex: failed to open session 0 : error 0x80000406 · failed to create device/session 0 · GGML_ASSERT(device) failed. The binary links the Hexagon backend directly rather than loading it on demand, so removing the library is not an option.

So this path is available only if the agent itself moves to it. That trade is known: the same Qwen3-4B as a Q4_0 GGUF on the Hexagon backend scored 98.5% on the 65-request canonical bench at 14.5 s per turn, against 7.3 s per turn on the compiled bundle. Context becomes a runtime knob on that path instead of a recompile, and a second server slot could in principle serve the readout beside the agent's prompts, which was not tested. The agent stays compiled; the decision layer goes to the CPU.

Path 4: the same binary, CPU-only, beside the tenant

The Snapdragon llama-server binary runs on the board's Kryo cores without touching the NPU once the Hexagon backend is told it has no devices. That is one environment variable, and it is the whole deployment trick.

LD_LIBRARY_PATH=$PWD/lib GGML_HEXAGON_NDEV=0 \ bin/llama-server -m Qwen3-4B-Instruct-2507-Q4_0.gguf \ -c 4096 -np 1 -t 6 --jinja --no-repack
GGML_HEXAGON_NDEV=0the backend registers zero devices, skips the DSP session and the model loads on the CPU while the production runtime keeps the NPU. Six of the eight cores are given to the server; one slot, so requests are sequential.

Latency was measured on a quiet board with the NPU tenant running: 20 requests per question after one warm-up request, one client, rotations off. The server reports how many prompt tokens it actually evaluated, which is the prefix cache doing its work: the command question's prompt is 666 tokens long and 20 of them are evaluated per request.

Board and dev-host columns are median wall time per request; p95 is the board; prompt time is the server's own prompt_ms on the board. Wall time is almost entirely prompt time: about 16 evaluated tokens per second on six Kryo threads, plus one decoded token. The gate state is the request plus the proposed call and its one-line description, hence 52 tokens and 3.1 s. The four-question benchmark battery is therefore about 5.1 s sequential, the production two-question pre-turn hook (tool, is_write) about 2.5 s, and one gate check per write 3.1 s. The development host, an aarch64 Grace CPU at 12 threads, answers the same requests in 0.56 to 1.32 s with the same server and protocol.

Co-tenancy costs nothing measurable. A generative turn through the production NPU runtime, with a 96-token answer, was timed with the CPU idle and again while the CPU readout answered a continuous stream of questions.

The other option: encoders on the CPU

An encoder needs none of the three properties above. It reads the state and the questions in one packed sequence and returns a distribution per question from its own head, so the serving path question does not arise: it runs under CPU torch in an isolated environment beside the tenant, and its cost is the forward pass.

Latency is only half of the choice. On the 126 held-out rows the fine-tuned encoder routes better than the 4B readout (tool 88.1% against 84.9%, command 77.8% against 69.8%), and on the 217 held-out gate pairs it does not learn the gate at all (AUROC, the area under the ROC curve, 0.556 for the balanced gate-only model against 0.967 for the readout). Single seed, one recipe. The division that follows is the one the main page draws: the encoder answers the per-turn router battery in milliseconds, the readout answers the per-write gate question in seconds, once per confirmation.

Porting checklist for another SoC

Each item is something that cost time here, in the order it would have saved the most.

  1. Probe the production runtime before designing around logits. Send it one request with max_tokens: 1 and logprobs: true, and read three fields: logprobs, completion_tokens and cached_tokens. Here they were null, 3 and 0.
  2. Search the runtime binary, not its changelog. Count the strings for n_probs and llama_get_logits; a front end that shows the OpenAI request struct can still implement none of it. Two versions on hand both returned 0 hits.
  3. Find out whether the accelerator is a single tenant. Start the second runtime while the first holds the device and keep the error text; here it was session error 0x80000406 followed by an assert.
  4. Find the backend's device-count knob. With GGML_HEXAGON_NDEV=0 one Snapdragon binary served the readout on the CPU beside the agent; a separate CPU-only build was not needed.
  5. Put the legend in the system message and check timings.prompt_n. It should equal the state's length. Here it was 20 of a 425-token prompt for the tool question and 52 of 205 for the gate.
  6. Loop rotation-major when averaging option rotations. All states for one rotation, then the next; with a single slot, cycling rotations per state thrashes the cache.
  7. Disable thinking in the chat template. A template that opens a thinking block puts zero mass on the labels at position 0; the readout sends enable_thinking: false.
  8. Measure co-tenancy with the production runtime running, and drop the first turn. Four idle turns and five loaded turns settled the question here; the first turn after idling took 9.97 s.
  9. Time the encoder at one and four threads. The 24-option question dominates every encoder battery (2.51 s of the fine-tuned model's battery for 126 ms per NOUL).
  10. Check that the runtime comes back after a reboot. On this board the container engine is socket-activated and disabled at boot, so the production runtime stays down until something touches it and the agent service runs against a dead backend.
